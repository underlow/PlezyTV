# S26 — Память и скорость запуска TV-интерфейса

Проект: `docs/projects/plezy-tv/project.md`, этап S26. Профиль `medium`.

> План проекта высокоуровневый: предпосылки этапа проверены в этом анализе (ниже), остальное — не проверено.

## 1. Цель и объём

Запрос (2026-10-27): S26 «Память и скорость на Mi Box 4». Пользователь: «сначала отчёт и советы», затем выбрал:
память — да. Показ главной из сохранённой копии до подключения сначала был выбран, затем снят пользователем
(«это мы не делаем»). Вместо него: ускорить подключение правкой в коде Plezy (решение пользователя, исключение из
правила «общий код не трогаем») и ускорить заполнение главной после подключения.

Устройство — Xiaomi `MiTV-AFKR0` (192.168.1.114, Android 11, 2 ГБ, 32-бит, режим `reduced`, Skia). Это не Mi Box 4,
но решено проверять на нём. Mi Box 4 и TCL — вне объёма, остаются непроверенными.

Исходные замеры (`main` @ `63b19753b`, release armv7):

- Главная через 20 с после холодного старта: PSS 350–375 МБ, из них графика 168 МБ. Оригинальный Plezy 2.24.0 на том
  же TV: 195–200 и 73 МБ.
- В простое на главной система сообщает о нехватке памяти, хотя кэш картинок пуст.
- Профилировщик: 261 декодированная картинка, 22 построенных ряда. Причина: вертикальный список главной
  (`SingleChildScrollView` + `Column`) строит все ряды сразу, каждый ряд держит видимую ширину плюс ещё один экран.
- Подключение к серверам: 2.1–8.7 с (7 запусков). Первый ряд появляется примерно через 2 с после него, остальные —
  ещё через 3–4 с. До подключения виден экран «Connecting to servers…».
- Самый медленный запуск (8.7 с, первый после долгого простоя): рабочий адрес ds920 найден за 0.3 с, затем при
  создании клиента сервера приложение ждёт ответ на запрос списка разделов `/media/providers`
  (`PlexClient.create` → `_initMediaProviders`, `lib/services/plex_client.dart`). Ответ пришёл примерно через 7 с,
  ожидание оборвалось по таймауту 6.5 с, повторное подключение прошло за 1 с. Запуски подряд — 2.1 с. Похоже, сервер
  медленно отвечает на первый запрос после простоя (догадка, не проверена).

**Точность замеров невысокая.** Числа зависят от содержимого главной на момент замера (сколько рядов и карточек,
какие картинки), от состояния сети и серверов и от прогона к прогону. Если главная поменяется, замер изменится. Цели
ниже — ориентиры. Сравнивать нужно на одном устройстве и одном сервере, в один день, по нескольким прогонам. Опорой
служит оригинальный Plezy, замеренный в тот же день.

Входит в этап:

- память TV-главной;
- такая же проверка поиска, фильма и сериала;
- подключение без ожидания списка разделов, если он сохранён с прошлого раза;
- более быстрое заполнение главной после подключения: одна загрузка при запуске, ряды каждого сервера по мере его
  ответа;
- скрипт замеров.

Не входит в этап:

- показ главной из сохранённой копии до подключения (снят пользователем);
- остальная логика подключения (поиск адреса, таймауты, проверка HTTPS);
- память при воспроизведении (S25);
- постеры при пустом кэше;
- мобильные экраны.

Риск: если сервер после простоя медленно отвечает на любой запрос, а не только на список разделов, ожидание
переедет на загрузку главной и выигрыш будет меньше. Это покажет замер после правки.

## 2. Требования

- **R1.** На главной через 20 с после холодного старта PSS ≤ ~250 МБ, графика ≤ ~100 МБ (Xiaomi, тот же сервер;
  с учётом точности замеров).
- **R2.** На главной декодированы картинки только рядов на экране и примерно на экран выше и ниже. Ряды дальше
  картинок не держат.
- **R3.** При движении вниз и вверх постеры следующего ряда появляются без заметного ожидания (кэш на диске
  тёплый). Без изменений остаются:
  - поведение S24: прокрутка к ряду, положение ряда, отступы;
  - запоминание карточки в каждом ряду, в том числе для ряда, ушедшего далеко за экран;
  - фокус в меню.
- **R4.** Круги главная → библиотека → фильм → назад не накапливают память: после первого круга следующие четыре
  увеличивают PSS не более чем на ~30 МБ, после пяти кругов PSS ≤ ~300 МБ. Рост на первом круге за счёт заполнения
  общего кэша картинок Flutter (бюджет 64 МБ) допустим.
- **R5.** В простое на главной 2 минуты нет сообщений «System memory pressure».
- **R6.** Поиск с результатами, страница фильма и страница сериала замеряются так же. Если экран держит больше
  ~60 картинок за пределами экрана, к нему применяется то же правило, что в R2.
- **R7.** Мобильные экраны и общий код не меняются, всё в `lib/plezytv/` и `scripts/plezytv/`. Исключения (решения
  пользователя), минимальные по объёму: правка для R9 в `lib/services/plex_client.dart` и хранение в
  `lib/services/storage_service.dart`; показ главной по серверам для R11 в `lib/providers/discover_provider.dart` и,
  если нужно, `lib/services/data_aggregation_service.dart`. Поведение мобильной главной меняется так же (общий код) —
  проверяется только тем, что её тесты проходят.
- **R8.** В репозитории есть скрипт замеров: холодный старт по фазам, PSS и графика, серия запусков, устройство
  задаётся параметром. Чтобы позже повторить на Mi Box 4 и TCL.

- **R9.** Если список разделов сервера уже был получен раньше для этого сервера и профиля, при следующем
  подключении приложение сразу работает с сохранённым списком и не ждёт ответа сервера на этот запрос. Свежий
  список запрашивается в фоне; если он отличается, меню и разделы обновляются без перезапуска (не позже чем через
  пару секунд после ответа). Нет сохранённого списка (первый запуск, новый сервер или профиль) — как сейчас.
  Ошибка фонового запроса — остаётся сохранённый список, как сейчас при ошибке остаётся пустой.
- **R10.** Сохранённый список разделов отдельный для каждого сервера и профиля (у разных профилей разные доступные
  разделы) и удаляется вместе с остальными сохранёнными ответами сервера (выход из аккаунта).
- **R11.** После подключения главная заполняется быстрее:
  - при запуске главная загружается один раз (сейчас дважды: вторая полная загрузка запускается сигналом о
    дочитанном списке скрытых разделов и ничего не меняет);
  - ряды сервера, ответившего первым, с постерами — не позже ~2 с после подключения, с учётом точности замеров;
  - ряды и карточки более медленных серверов добавляются по их ответу, без перезагрузки главной и без повторных
    запросов к уже ответившим серверам.

  Замер до правки (Xiaomi, два сервера: ds920 в локальной сети, «Drtinator 2» через интернет): от подключения до
  заполненных рядов 4–8 с; из них 1.3–3.5 с — вторая загрузка, остальное — ожидание «Drtinator 2» (первый запрос
  рядов 2.8–4.8 с; ds920 отвечает за 0.2–0.8 с).
- **R12.** Когда добавляются ряды медленного сервера: фокус остаётся на той же карточке, её ряд не сдвигается на
  экране; новые ряды встают на свои места по порядку разделов; «Продолжить просмотр» дополняется карточками. Сервер
  не ответил или ответил ошибкой — как сейчас: его рядов нет, главная не падает и не показывает ошибку, если есть
  ряды других серверов.

## 3. Дизайн

**Ленивая главная.**

- Вертикальный список `TvHomeScreen` становится ленивым: строит ряды в пределах примерно экрана выше и ниже
  видимой области.
- Высоты рядов известны из токенов. Поэтому программная прокрутка к ряду (`_revealRow`) считает смещение без
  построения рядов.
- Запоминание карточки и горизонтальной прокрутки в ряду: `TvHorizontalRow` по-прежнему хранит их сам, если
  владелец не передал своё хранилище. Главная передаёт своё, по ключу ряда, чтобы память пережила удаление ряда из
  дерева и ряд при повторном построении стоял там же, где был. Остальные экраны
  (фильм, сериал, поиск, библиотека, после просмотра, плеер) не меняются.
- Запас прокрутки внутри ряда уменьшается с одного экрана до половины, если замер покажет, что это нужно для R1.
- Для поиска, фильма и сериала — то же правило, если они не проходят R6.
- R2 считает картинки, которые держат виджеты. Картинки удалённых рядов могут оставаться в общем кэше Flutter
  (бюджет 64 МБ в режиме `reduced`, `device_performance.dart`) до вытеснения; он входит в общий бюджет R1, его
  настройки не меняются (общий код).

**Список разделов с прошлого раза.**

- В `PlexClient.create` (`plex_client.dart`): если для сервера и профиля есть сохранённый ответ `/media/providers`,
  разобрать и применить его сразу, а свежий запрос выполнить в фоне и применить по ответу. Без сохранённого —
  ожидание, как сейчас. Хранение — рядом с сохранённым рабочим адресом сервера (`StorageService`,
  `server_endpoint_*`): ключ по серверу и профилю, чистится там же, где адреса (`clearMultiServerData` при выходе из
  аккаунта). `ApiCache` не подходит: его обычные записи стираются при каждом начале сессии профиля
  (`ApiCache.clearRegisteredVolatile` в `profile_session_screen.dart`).
- Свежий ответ, отличный от сохранённого, должен дойти до меню и разделов: клиент сообщает об изменении, и список
  разделов (`LibrariesProvider`) перезагружается. Где подписаться — в TV-коде сессии, если без правки другого общего
  кода можно; иначе `needs-decision`.

**Главная после подключения.** Главная строит только ближние ряды (выше), поэтому картинки невидимых рядов не
занимают процессор и сеть, пока грузятся видимые.

- Одна загрузка — в TV-коде: TV-главная до первой загрузки дожидается списка скрытых разделов
  (`HiddenLibrariesProvider.ensureInitialized`) и не запускает загрузку, если она уже идёт. Сама гонка в
  `DiscoverProvider` (`_onHiddenLibrariesChanged` срабатывает до того, как проход запомнил ключи) остаётся в общем
  коде.
- Показ по серверам — в `DiscoverProvider`: полный проход публикует результат, как только ответил первый сервер,
  с короткой паузой (~0.3 с), чтобы близкие по времени ответы пришли одним обновлением. Серверы, ещё не ответившие
  к этому моменту, вклеиваются существующим механизмом дозагрузки серверов (`_loadDeltaOnce`, порядок рядов по
  разделам) по уже отправленным запросам, без повторной отправки. Ошибки, отмена, смена профиля, скрытые разделы —
  по существующим правилам прохода.
- TV-главная при вставке рядов сохраняет фокус и положение фокусного ряда на экране (R12). Отметка `TV home rows
  ready` — по готовности видимых рядов, не дожидаясь медленных серверов.

**Замеры.** Скрипт в `scripts/plezytv/`: холодные старты с фазами из logcat (`Startup phase`), время до заполненной главной (по скриншотам или
отметке TV-кода в logcat), PSS и графика из
`dumpsys meminfo`, параметр устройства и пакета. Подсчёт картинок — через VM service профильной сборки
(`scripts/perf/vmclient.mjs`).

## 5. Согласование

Первая версия подтверждена пользователем 2026-10-27 с поправкой: «точность невысокая, если страница поменяется —
замер изменится» (внесено в раздел 1 и пороги). Затем пользователь снял показ главной из сохранённой копии при
запуске и выбрал: подключение — правка в коде Plezy, вариант «список разделов с прошлого раза» (`plex_client.dart`,
исключение из правила); главная после подключения — да, без отдельного исследования. Требования перенумерованы.
Эта версия подтверждена пользователем 2026-10-27 перед реализацией.

Изменение при реализации (2026-10-27, решение пользователя): R4 и A4 переформулированы. Замер после T2 на Xiaomi:
211 → 289 МБ на первом круге (общий кэш картинок Flutter заполняется до бюджета 64 МБ, главная теперь держит в нём
~12 МБ), круги 2–5 — +6 МБ, после пяти — 295 МБ (до T2: 353 → 399 МБ). Требование задумано против накопления; бюджет
кэша — общий код (R7), не меняется.

Делегировано координатору: точная ширина запаса для рядов (в пределах R1–R3), оформление скрипта замеров.

Изменение при реализации (2026-10-27, решение пользователя после исследования R11 на Xiaomi): R11 переписан
(одна загрузка, ряды по серверам), добавлен R12 и A15–A18, A13 уточнён, R7 расширен на
`lib/providers/discover_provider.dart` и `lib/services/data_aggregation_service.dart`.
